# 跨平台本地显示分辨率策略设计

## 目标

FreeRemoteDesk 在 Windows、macOS 和 Linux 桌面客户端上统一表达远程桌面分辨率意图，同时保留各协议和平台的能力边界。默认优先使用当前本地显示器的物理像素尺寸，不设置 2560×1440 的产品上限；协议、GPU 纹理尺寸和帧缓冲预算只作为实际安全上限。

## 用户可见模式

客户端提供以下协议无关的模式：

- **显示器原生**（默认）：请求当前显示器的物理分辨率。全屏时跟随当前显示器，窗口化时使用当前显示器的物理尺寸作为初始目标；窗口尺寸变化由支持的协议动态调整。
- **显示器工作区**：排除菜单栏、Dock、任务栏和系统保留区域后，以工作区物理尺寸作为目标。
- **窗口内容**：以远程内容区域的物理尺寸作为目标，保留窗口标题栏和系统边框。
- **固定尺寸**：用户选择或输入固定宽高，例如 1280×720、1920×1080、3840×2160 或更高尺寸。
- **服务器管理**：不发送本地尺寸偏好，由服务器和协议默认值决定。

分辨率和界面缩放独立。Retina 或其他高 DPI 显示器的逻辑点会转换为物理像素后发送到远端，例如 1728×1117 @2 对应约 3456×2234 的远程目标。窗口的本地逻辑尺寸仍由宿主窗口系统管理，不能把物理像素直接当作逻辑点使用。

## 目标尺寸计算

`DisplayGeometry` 由平台窗口适配器产生，包含逻辑尺寸、物理尺寸、工作区、远程内容矩形、缩放因子和全屏状态。`DisplayPlanner` 根据 `ResolutionMode` 选择候选物理尺寸，然后按以下约束做一次保持宽高比的收敛：

1. 协议能力声明的最大宽度、高度或面积；
2. 客户端 GPU 纹理尺寸；
3. 客户端帧缓冲内存预算（按每像素字节数计算）。

没有固定的 2560×1440 上限。约束导致尺寸缩小时，计划结果携带原因，供诊断和 UI 提示使用；不能静默伪装成用户请求的尺寸。零尺寸、整数溢出和超过协议可表达范围的输入必须在规划阶段拒绝或安全收敛。

没有明确选择多显示器时，只使用当前显示器。多显示器布局属于单独能力，必须同时得到用户选择和协议能力支持。

## 协议适配

- **RDP**：连接请求携带初始 `DisplayIntent`。连接器在协商前按本地几何计算初始 DesktopSize，而不是使用固定 1280×720。协商出 Display Control 后，沿用现有 latest-only、精确确认、generation 和完整基线规则处理后续尺寸；不支持时保持初始尺寸并显示受限原因。
- **Apple HPSS**：只在已有高性能虚拟显示器握手和动态分辨率证据满足时使用本地目标；尺寸提交、确认和帧基线切换保持 Apple 自己的状态机。不得引入 RDP 类型或字段。
- **Apple Standard/MVS、VNC 和其他固定协议**：传递服务器管理或固定尺寸意图；当协议不能改变远端桌面尺寸时只做本地缩放，不能假装完成远端重设。

所有协议都保留旧表面，直到新尺寸获得精确确认并收到完整首帧；这样分辨率切换不会再次产生黑屏。

## 窗口和交互

登录页和设置页选择模式，默认选中“显示器原生”。远程会话开始后，状态和错误进入标题栏/窗口 chrome，远程内容区域不额外保留工具栏。当前显示器改变、窗口内容区域改变或全屏状态改变时，平台适配器更新 `DisplayGeometry`；只有协议明确支持动态尺寸且会话证据满足时才提交新目标。

## 安全和兼容性

分辨率意图不包含凭据或证书数据，不进入日志中的秘密字段。`ConnectRequest` 增加协议无关的显示意图字段，旧的直接构造请求使用服务器管理默认值；Windows 平台的认证、证书 TOFU、黑屏基线和现有输入路径保持不变。README 平台矩阵分别记录客户端平台、远端操作系统、实现状态和验证范围。
