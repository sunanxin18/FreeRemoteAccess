# RDP EGFX/H.264 验证记录（2026-09-07；2026-09-08 continuation）

本记录只描述当前工作区已经执行的检查和仍然关闭的生产门禁。编译、单元测试、
FFmpeg ABI 合同和离线选择器测试不等于 RDP EGFX 真实互操作。Windows/macOS 组合根
现在会在固定 FFmpeg bundle 成功加载且 AVC420 能力精确匹配时注入 EGFX provider；
bundle 缺失或能力不匹配时仍保持 Bitmap/RemoteFX legacy-only。2026-09-08 的
macOS arm64 bundle 已重新构建为 H.264+HEVC decoder/parser，并通过包签名、架构、依赖、
ABI 和 codec verifier；授权 Windows 目标上的 opt-in probe 成功加载本地 AVC420 provider，
但没有产生可归因于 EGFX 的第二个 `ResetGraphics`/EGFX surface 更新，因此真实 EGFX
首帧、持续刷新和恢复门禁仍关闭；生产组合根只有在这个签名 bundle 能力精确匹配时才
广告 AVC420，不能据此把会话升级为 H.264 首选。

2026-09-08 在提交 `cec575f` 上完成了一次 legacy-only 有界 Windows RDP 回归：
1280×720 首个完整 baseline、20 秒内 169 个 frame boundary/169 个 patch/2 个
FullBaseline，随后显式断开并正常回收。该探针没有注册 EGFX decoder provider，因而只
证明 Bitmap/RemoteFX fallback 仍可用；它不提供 RDPGFX `CapabilitiesConfirm`、AVC420、
AVC444 或 HEVC 的服务器互操作证据。

## EGFX AVC420 bounded probe 接线

`crates/frd-protocol-rdp/examples/bounded_live_probe.rs` 现在保留默认
legacy-only 行为，并增加了显式环境变量 opt-in。只有同时设置
`FRD_RDP_PROBE_EGFX_AVC420=1` 和 `FRD_RDP_PROBE_MACOS_APP=/absolute/path/FreeRemoteDesk.app`
时，probe 才会从指定的 macOS `.app` 加载 FFmpeg backend，复用签名、包内路径、固定
FFmpeg 版本和 ABI 校验，并把精确的 H.264/AVC420、YUV420、8-bit provider 注入
`RdpProtocolFactory`。凭据仍只从非终端 stdin 管道读取，环境变量不承载凭据；默认不设
上述变量时不会加载 backend、不会广告 EGFX。

probe 只输出本地 backend 能力、provider 是否附着、首帧时间、frame boundary、baseline、
patch、解码字节数和断开回收结果。例如启用后会输出
`local_capability=software_exact provider=attached server_confirmation=pending`；这行是
本地能力证据，不是服务器确认。当前公开的 `SurfaceUpdate` 合同没有携带 EGFX/legacy
来源标签，因此最终 frame 统计也不会冒充 EGFX 首帧或持续刷新证明；仍必须在授权目标上
执行真实 `CapabilitiesConfirm → ResetGraphics → AVC420 first frame → sustained refresh →
recovery` 观察，并将结果另行记录。

### EGFX channel advertisement fix

离线 wire 检查发现 pinned IronRDP connector 默认没有把
`SUPPORT_DYN_VC_GFX_PROTOCOL`（`RNS_UD_CS_SUPPORT_DYNVC_GFX_PROTOCOL`，`0x0100`）写入
`TS_UD_CS_CORE.earlyCapabilityFlags`；仅注册 `EgfxAdapter` 因而不足以让 Windows 打开
`Microsoft::Windows::RDS::Graphics` DVC。现在根目录通过
`third_party/ironrdp-connector-0.10.0` 保留一个最小、可审计的本地补丁：只有精确 decoder
provider 已注入时，`frd-protocol-rdp` 才把该位置上；legacy connector 的默认值仍为
`false`。`connector::tests::egfx_provider_emits_the_graphics_channel_capability_on_the_wire`
和 `legacy_connector_omits_the_graphics_channel_capability_on_the_wire` 会分别实际编码并
重新解析有/无 provider 的 MCS Connect Initial，验证 wire bit，而不是只检查内存中的配置字段。
该修复解决了客户端广告链路的已知缺口，但没有替代目标服务器的
`CapabilitiesConfirm → ResetGraphics → AVC420 first frame` 真实证据；当前授权 probe 尚未
重跑，因此生产 EGFX/AVC420 门禁仍保持关闭。由于 pinned IronRDP 的 decoder reset 接口不携带
尺寸，publisher 现在把服务器 `ResetGraphics` 与 decoder 建立时的 coded size 做精确比较；
尺寸不一致时在入队 runtime Reset 前禁用 EGFX，并保留 legacy Bitmap/RemoteFX surface，避免
远端服务端调整请求分辨率后出现 decoder 与 framebuffer 尺寸错配。

## 2026-09-08 opt-in probe 结果

使用当前 release `.app` 内的 FFmpeg 8.1.2 bundle 运行了显式 AVC420 opt-in probe。非敏感
结果为：`backend=ffmpeg-8.1.2-software local_capability=software_exact
provider=attached`。新增的非敏感 graphics observer 报告
`egfx_advertised=true egfx_confirmed=false avc420=false avc444=false`；连接通过
TLS/CredSSP/NLA，协商桌面为 1280×720，首帧约 1325 ms，20 秒内观察到
`resets=1 frames=110 full_baselines=2 patches=110 decoded_bytes=28000256`，主动断开后
worker 正常回收。当前 `SurfaceUpdate` 仍不携带来源标签；结合只有一个 legacy generation
reset，不能把这些帧计为 EGFX AVC420 帧。该目标本次没有提供
`CapabilitiesConfirm → ResetGraphics → AVC420 first frame` 的可审计证据，所以真实
AVC420 首帧门禁、AVC444 接线和 HEVC 首选均保持关闭；生产组合根仍只在签名 bundle
能力精确匹配时广告 AVC420，Bitmap/RemoteFX 回退的成功结果与此前 legacy-only 观察一致。

## 尚未打开的生产门禁

1. `baseline_connector` 只在组合根提供精确 decoder provider 且能创建 EGFX decoder 时注册
   `EgfxAdapter`；没有 provider 时 `RdpGraphicsCapability` 中 `egfx_advertised`、
   `egfx_confirmed`、`avc420`、`avc444` 继续为 `false`。当前 Windows/macOS 的 bundle
   加载失败路径已回退到该默认状态。
2. 产品级应用已经提供固定 FFmpeg bundle 的 AVC420 provider 注入，但尚未完成真实
   `CapabilitiesConfirm → ResetGraphics → AVC420 first frame → sustained refresh →
   recovery` 测试。协议层 provider 失败时会禁用 EGFX stream 并让外围 ActiveStage
   继续 legacy 处理；服务器在已经收到 EGFX 广告后是否发送可用 legacy 更新仍需 live
   证据。YUV420→RGBA 已有 AArch64 NEON/x86 SSE4.1 leaf kernel 和本机 parity 测试；
   Windows/Linux 目标编译、性能门槛和 bundle 级验证仍未通过。
3. AVC444 的 RDP wire profile 尚未由服务器证据确认；HEVC 的 RDP wire profile 和
   所有目标平台的真实生产互操作也尚未确认。因此 selector 只能作为 fail-closed
   规划接口存在，不能改变当前连接路径。
4. 没有把 Bitmap/RemoteFX 回退移除；没有 EGFX 或 decoder 失败时必须继续使用现有
   legacy surface path。

后续只有在逐目标 package、原生 decoder fixture、真实 EGFX 互操作和恢复测试都通过
后，才可以把对应 codec 从 `开发中` 提升到 `受限验证` 或 `已验证`。

补充：`cargo test --locked --workspace --quiet` 已能完成跨平台 root crate 的链接，
但在既有 `frd-icon-assets` 确定性导出测试中失败（`apple/foreground.png` 已提交字节
与当前生成器不一致）。该失败与 RDP/EGFX 改动无关，未重写用户的图标资产；RDP、媒体
和 FFmpeg focused suites 仍单独通过。
