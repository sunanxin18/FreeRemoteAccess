# RDP EGFX H.264 解码 Implementation Plan

> 2026-09-08 用户调整构建范围：macOS 仅构建 ARM64；Intel/x86_64 不支持当前构建与发布，不再是交付门禁。此前 Intel/Rosetta 结果仅保留为历史证据。Windows/Linux 的 x86、x86_64、ARM64 范围不变。

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在现有 Bitmap/RemoteFX 回退不变的前提下，按 AVC420 → RemoteFX 优化 → AVC444 → HEVC 的顺序，为 RDP 增加基于真实能力确认的图形解码路径，并覆盖目标 CPU 架构。HEVC 最后实现和验证；通过真实生产互操作门禁后，运行时首选 HEVC。

2026-09-08 协议坐标审计修正 pinned `ironrdp-egfx` 的 AVC420/AVC444 元数据解析：`RDPGFX_RECT16` 的 right/bottom 现在按规范作为排他边界解码；服务器侧 `Avc420Region` 仍保留 inclusive 便于现有发送 API，并只在编码边界转换。AVC420 客户端和 AVC444 校验/发布路径均移除重复加一，AVC444 内部重建仍使用归一化后的 inclusive 表示；空或反向区域在 PDU 解码边界直接拒绝；decoder reset health gate 会在 runtime Reset 发布前拦截失败；YUV 平面 stride 的长度计算使用 checked arithmetic，溢出会在转换边界 fail-closed，并保留 zero-height 非零宽度 plane 校验契约；本地验证阶梯现在直接运行 pinned crate 的 19 项测试，另有 RDP 185 项测试和 workspace 全量测试均通过。

当前补充：FFmpeg loader 提供 `supports_hevc_main4448()` 只读探针并有 H.264-only 负向回归测试；它只证明本地 HEVC Main4448/YUV444P8 backend 能力，不改变 RDP connector 的广告、协商或选择。native plugin 的 capability bits 现在还必须由 FFmpeg decoder 的 profile 列表和 `avcodec_get_supported_config(AV_CODEC_CONFIG_PIX_FORMAT)` 明确声明对应 profile/YUV 输出后才设置，不能仅以 codec 存在或像素格式枚举值存在推断，解码后的 frame-format 校验继续作为第二道门禁。YUV 平面 stride 溢出修复后的本机阶梯结果已记录在 `docs/validation/windows-native-rdp.md`，真实 RDP HEVC wire profile 仍是后续门禁。

**Architecture:** 保持 IronRDP transport/session 与窗口/renderer 正交；增加独立 EGFX DVC adapter，将编码视频 payload 交给协议中立 `VideoDecoderRegistry`。先实现 AVC420 H.264 软件正确性 backend，再完成 RemoteFX 优化、AVC444，最后才处理 HEVC。平台硬件 decoder 和汇编/SIMD 只作为精确能力匹配后的实现，不改变 `SurfaceUpdate`。

## Global Constraints

- 不得在没有真实 decoder 的情况下广告 AVC420/AVC444。
- 不得把 FFmpeg 直接依赖注入 `frd-protocol-rdp`；RDP adapter 只能使用协议中立 decoder factory。
- 保留现有 Bitmap/RemoteFX fallback，并确保没有 EGFX 的 Windows Server 行为不变。
- 实现顺序固定为 AVC420、RemoteFX 优化、AVC444、HEVC；不得因为本地显卡探针或
  离线 fixture 通过就提前启用 HEVC。
- 运行时选择顺序独立于实现顺序：HEVC 完成真实生产互操作验证且服务器实际协商
  后优先使用 HEVC；失败再回退到已验证的 AVC420/AVC444、RemoteFX、Bitmap。
- HEVC、AVC 和 legacy codec 都必须使用精确的 wire profile、像素格式、分辨率和
  decoder backend 能力匹配，不能用“支持某个编码名称”替代能力确认。
- IronRDP 协议状态机、能力协商和 generation/frame 状态保持可移植 Rust；生产
  软件解码的 codec/copy 热点必须使用目标架构的汇编或 SIMD，优先复用 FFmpeg
  已验证的 x86/x86_64 与 AArch64/NEON 实现。
- Rust 标量路径只能作为参考实现、确定性测试 oracle 或显式 unsupported-CPU
  回退，不能静默成为已支持架构的生产解码器。每个架构都必须有编译、运行时特性、
  逐像素一致性和基准门禁。
- Windows i686/x86_64/arm64、Linux i686/x86_64/arm64、macOS x86_64/arm64 必须分别拥有构建或明确的 unavailable gate。
- 不进入源代码、日志、fixture 或命令行的真实凭据和服务器身份。
- 更新 README 平台矩阵和验证记录；编译、离线 fixture、package staging 与真实互操作必须分开表述。
